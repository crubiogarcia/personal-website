Geometric Compliance Engine

APPLIED AI · COMPUTATIONAL GEOMETRY · STRUCTURED DATA

Translating natural-language building regulations into computable geometric rules.

three.js · llm pipeline · rule engine

Overview

Geometric Compliance Engine is a research prototype exploring how building regulations written in natural language can be translated into rules that can be checked against a 3D building model.

The system uses a language model to identify relevant requirements in a building code and translate them into a structured format. These rules are then evaluated against data from the building model using deterministic code.

For the current prototype, I focused on accessibility requirements for doors. When a rule fails, the system identifies the affected element, highlights it in the 3D model, and keeps a reference to the original regulation.

The prototype is built with a browser-based 3D viewer in Three.js, an LLM-based pipeline for extracting and structuring the regulatory text, and a deterministic rule engine that evaluates the resulting rules against structured 3D model data.

01 — Interpreting building regulations

Turning a legal document into structured requirements

Building regulations contain hundreds of requirements written in natural language, often mixed with diagrams, exceptions and references to other parts of the document.

The first stage uses a language model to find the requirements related to a particular type of building element — in this prototype, doors. These include minimum opening widths, clearance requirements, threshold conditions and relationships with stairs and ramps.

Rather than asking the model directly whether a building complies, the system first extracts the relevant clauses and keeps their source, section and context.

This provides a structured intermediate step between the original regulation and the geometric checks that follow.

02 — From language to geometric rules

Turning a requirement into something that can be evaluated

Once a relevant clause has been found, it is translated into a simple machine-readable rule.

For example:

“Accessible doors must provide a minimum clear opening width of 800 mm.” → Door → width ≥ 800 mm

Each rule contains:

Rule structure
ElementDoor
Propertywidth
Operator≥
Value800 mm
SourceOriginal regulation + section + page

The language model is used to interpret the regulation, but it does not make the final compliance decision.

AI INTERPRETS THE CODE · DETERMINISTIC CODE PERFORMS THE CHECK

Once the rule has been generated, regular code evaluates it against the building model. This keeps the interpretation step separate from the final calculation and makes the result easier to trace.

03 — Representing the building as data

What does the system actually know about a door?

The other side of the problem is the information available in the 3D building model. For each door, the prototype currently extracts:

  • Unique ID
  • Name
  • Width
  • Height
  • Internal / external classification
  • Level

The language model is only allowed to generate rules using information that the system knows how to retrieve from the model.

This is where one of the main limitations becomes visible. Regulations often describe things that are not stored as simple properties of an individual element.

Regulation describes
clear opening · threshold · turning space · distance to stair · clear space · accessible route · …
↓
Model directly contains
width · height · classification · level · …

What the system can evaluate therefore depends on how much of the regulation can be expressed using the information available in the model.

04 — Compliance evaluation

Checking the rules against the model

Once a rule has been generated, a deterministic rule engine checks it against every relevant element.

Model value → operator → requirement → PASS / FAIL

For example:

Door #216401
Width762 mm
Required≥ 800 mm
ResultFAIL

For each failed check, the system keeps:

  • Actual value
  • Required value
  • Issue description
  • Source document
  • Source section
  • Source page

This creates a traceable connection between: building element ↔ failed rule ↔ source regulation.

So the result shows not only what failed, but also which requirement caused it and where that requirement came from.

05 — Connecting the result back to geometry

Making violations visible in the model

The compliance results are then mapped back onto the 3D building model.

3D model → element IDs → rule evaluation → failed IDs → highlighted geometry

Each element has an ID that connects the data used during the check with its geometry in the viewer. When an element fails, that same ID is used to highlight it directly in the model.

This makes the result easier to understand spatially, rather than presenting compliance only as a list of errors.

06 — Where the first approach breaks down

Regulations describe relationships, not just properties

One of the most useful results of the prototype was finding where this simple rule representation stops working.

A rule such as: door.width ≥ 800 works because width is already available as a property of the door.

But many regulations describe relationships between an element and its surroundings:

  • Distance between a door and a staircase
  • Clear space in front of a door
  • Threshold height
  • Whether a door belongs to an accessible route

These relationships are not directly stored as properties of the door.

Because the first version of the system cannot represent them, it can sometimes generate rules that look correct structurally but do not capture what the regulation actually means.

For example:

Regulation

Minimum horizontal distance between a door and a stair: 400 mm

Generated rule door.width ≥ 400

Or:

Regulation

Maximum threshold height: 50 mm

Generated rule door.height ≤ 50

The problem is not simply that the generated values are wrong. The system is trying to describe a spatial relationship using the wrong type of representation.

This exposed the main research problem behind the prototype: many building regulations describe relationships between objects and their surroundings, rather than properties of individual objects.

From properties to geometric relationships

The next step is to extend the system beyond simple property checks and represent these spatial relationships directly.

Instead of only evaluating: door.width ≥ 800 the system would need to handle rules such as:

  • distance(door, stair) ≥ 400
  • threshold_height(door) ≤ 50
  • clear_space_in_front_of(door) ≥ 1200
  • IF door ∈ accessible_route THEN clear_width(door) ≥ 800

These values need to be derived from geometry and context rather than simply read from the model.

This leads to the broader question behind the project: how can requirements written in natural language be translated into geometric relationships that a computer can evaluate?

The next stage of the research focuses on building these geometric relationships directly from the 3D model.

Simple property rule door.width ≥ 800
Spatial rule distance(door, stair) ≥ 400
Contextual rule IF door ∈ accessible_route → width ≥ 800
